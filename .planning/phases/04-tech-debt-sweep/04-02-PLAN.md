<objective>
Replace the hardcoded green "CI · Passing" badge in the TopBar with live GitHub Actions status. The TopBar is the recruiter's first impression of the IDE chrome — a green badge that stays green no matter what state CI is actually in is dishonest portfolio polish. This phase wires the badge to the real workflow run conclusion on `main` with a 5-minute ISR cache, a silent green-fallback on errors (per D-02), and a new red tone for the failing state. The other two badges (`Coverage · 98%`, `Tests · 312`) stay static — they are explicitly decorative for v1 per D-03 and are out of scope.

Purpose: A live CI badge proves the candidate's portfolio is held to the same accountability bar as any production system they would ship for an employer. Failing-state visibility is the whole point — if a recruiter visits during a red main, they see the truth and the candidate's response time becomes the story.

Output: New route handler at `src/app/api/ci-status/route.ts` returning `{ passing: boolean }` with `runtime = 'nodejs'` and `revalidate = 300`. Modified `TopBar.tsx` with a one-shot useEffect fetch and a `ciPassing` state defaulting to `true` (green fallback). Modified `TopBar.module.css` adding a `.toneRed` block following the same 4-selector structure as `.toneGreen` and `.toneBlue`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| visitor browser → /api/ci-status (Vercel Node fn) | No untrusted input from the visitor — handler is a parameterless GET; the only inputs are server-side env vars |
| /api/ci-status (Vercel Node fn) → api.github.com | Server-side outbound; Bearer token is server-only and never echoed to the visitor |
| TopBar `<StatusBadge>` render → DOM | `tone`, `value`, `label` are typed string literals rendered as React children inside `<span>` — no innerHTML path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05 | Information Disclosure | /api/ci-status response body | mitigate | Task 1 acceptance criteria require the success body to be exactly `{ passing: boolean }` — no token, no env vars, no upstream URL, no raw GitHub fields. Verified by code review against the acceptance grep (`! grep console.* GITHUB_TOKEN`) and by the explicit response shape constraint. |
| T-04-06 | Information Disclosure | Server logs | mitigate | Task 1 forbids `console.log/warn/error` lines referencing `GITHUB_TOKEN` or `token`. The route does not log at all — silent success or a generic 503/upstream-status envelope. |
| T-04-07 | Denial of Service | /api/ci-status hit by automated traffic burning GitHub API quota | mitigate | `export const revalidate = 300` caches the route response for 5 minutes per D-04. Even a recruiter-HN spike will resolve to one GitHub API call every 5 minutes. No per-IP rate limit needed for a cached GET. |
| T-04-08 | Tampering | Malicious response from api.github.com | accept | GitHub API is a trusted dependency (already used by Phase 3 /api/run-status); we only read the boolean conclusion field — no string is reflected back to the client unfiltered. If GitHub returns malformed JSON, `res.json()` throws → unhandled rejection → Next.js returns a 500; TopBar `.catch` silently keeps the green fallback. |
| T-04-09 | Elevation of Privilege | Token scope abuse if GITHUB_TOKEN leaks | accept | Token scope is `actions:read` only (set in Phase 3 — no write/admin scopes). Even a leak grants read-only visibility into already-public workflow run metadata. Documented in user_setup.env_vars. |
| T-04-10 | Spoofing | Client sets `ciPassing` directly bypassing the fetch | accept | Client-side state is not a security boundary — `ciPassing` is presentational only. A malicious user editing their own DOM to see a different badge color affects no other user and exposes no data. |
| T-04-11 | Tampering | XSS via tone/value rendering | accept | StatusBadge renders `tone`, `value`, and `label` as React children inside `<span>` elements — no `dangerouslySetInnerHTML`, no `href`, no `src`. The tone union is constrained to three string literals at the TypeScript boundary. |
</threat_model>
