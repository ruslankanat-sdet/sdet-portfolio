## Critical Issues

### CR-01: CI badge silently shows "Failing" on HTTP error responses — violates D-02

**File:** `src/components/ide/TopBar.tsx:57-65`

**Issue:** The `fetch('/api/ci-status')` chain does not check `r.ok` before calling `r.json()`. When the route handler returns a non-2xx response (503 when `GITHUB_TOKEN` / `GH_OWNER` / `GH_REPO` env vars are absent, or a passthrough status if the GitHub API returns 4xx/5xx), the response body is `{ error: '...' }`, which has no `passing` property. `data.passing` resolves to `undefined`. `setCiPassing(undefined)` stores a falsy value, so `ciPassing ? 'green' : 'red'` evaluates to `'red'` and the badge displays "CI · Failing". This directly contradicts the comment on line 53–54 (`// Fallback: keep "Passing" / green as the loading and error state (D-02)`) and the `.catch(() => {})` block that is supposed to hold green on network failure. The HTTP-error code path is not covered by that catch, only network-level exceptions are.

**Fix:**
```ts
fetch('/api/ci-status')
  .then((r) => {
    if (!r.ok) return;          // non-2xx → keep green fallback, no state update
    return r.json();
  })
  .then((data?: { passing: boolean }) => {
    if (data !== undefined) {
      setCiPassing(data.passing);
    }
  })
  .catch(() => {
    // silently keep the green fallback (D-02)
  });
```

### CR-02: Clock displays browser-local time but labels it "UTC+5" — misleading for every non-UTC+5 visitor

**File:** `src/components/ide/TopBar.tsx:41-51` and `src/components/ide/TopBar.tsx:117`

**Issue:** Both `useState` initializer and the `setInterval` tick call `new Date().toLocaleTimeString('en-US', { hour: '2-digit', minute: '2-digit', hour12: false })` without a `timeZone` option. This returns the time in the browser's local timezone. The rendered label `<span className={styles.clockTz}>UTC+5</span>` (line 117) is hardcoded. A recruiter visiting from San Francisco (UTC-7) will see their local time labelled "UTC+5" — 12 hours off from reality. The intent is clearly to show the candidate's local time (Almaty/UTC+5), but the implementation shows the visitor's local time.

Additionally, the `useState` lazy initializer runs during server-side rendering with the server's timezone. If the server is UTC and the client is UTC+5, the initial render will show a different time than the hydrated value, causing a React hydration mismatch warning (and potential visible flicker).

**Fix:** Pass the `timeZone` option to both `toLocaleTimeString` calls and add `suppressHydrationWarning` to the containing span, or move clock initialisation to `useEffect` only (initialise to `''` in state):

```ts
// Option A: render clock only after mount (avoids hydration mismatch entirely)
const [time, setTime] = useState<string>('');

useEffect(() => {
  const fmt = () =>
    new Date().toLocaleTimeString('en-US', {
      hour: '2-digit',
      minute: '2-digit',
      hour12: false,
      timeZone: 'Asia/Almaty',   // UTC+5 / Almaty
    });
  setTime(fmt());
  const id = setInterval(() => setTime(fmt()), 30_000);
  return () => clearInterval(id);
}, []);
```

## Warnings

### WR-01: `addInitScript` stacking order relied upon to override `beforeEach` state — fragile

**File:** `e2e/recruiter.spec.ts:108-132`

**Issue:** Tests `REC-11` and `IDE-01` call `page.addInitScript()` inside the test body to register a second localStorage script that overrides the `'recruiter'` mode set by the describe-level `beforeEach`. The comment on line 110 states "addInitScript scripts run in registration order — later registration wins". This is correct behaviour in the current Playwright version (scripts run serially in registration order before each navigation), but:

1. It is not documented as a stable API guarantee in the Playwright spec.
2. The override mechanism is subtle: the `beforeEach` always runs first and queues its script; then the test body queues a second script. A developer reading the test body in isolation cannot tell that a `beforeEach` is also running.
3. Any future refactor that adds `page.context().clearCookies()` / `page.context().clearPermissions()` between beforeEach and test body could reorder or reset scripts without warning.

The same pattern appears in the navigation spec (line 22): `addInitScript` is called in the test body of test 2, which has no `beforeEach`, so there is no conflict there — that usage is fine.

**Fix:** Explicitly clear and re-set the storage state rather than relying on script ordering. Use `page.context().storageState()` or add a `localStorage.removeItem` / `localStorage.setItem` call inside `page.addInitScript` that unconditionally sets the desired value:

```ts
// In the test body of REC-11:
// Instead of relying on ordering, clear and set atomically:
await page.addInitScript(() => {
  // Explicitly clear to avoid any prior script's value
  localStorage.removeItem('resume-mode');
  localStorage.setItem('resume-mode', 'ide');
});
```

Or restructure REC-11 into a separate `describe` block with its own `beforeEach` that sets `ide` mode.

### WR-02: Unit test `REC-08` does not assert `noreferrer` — unit test is weaker than the E2E test

**File:** `src/components/recruiter/__tests__/RecruiterView.test.tsx:141-149`

**Issue:** The E2E test in `e2e/recruiter.spec.ts` lines 85-93 asserts both `noopener` **and** `noreferrer` on the GitHub and LinkedIn links. The corresponding unit test in `RecruiterView.test.tsx` lines 141-149 asserts only `noopener`. If `noreferrer` were removed from the source (`ContactSection.tsx`), the unit test would pass (false green) while the E2E would fail. The unit test provides incomplete safety coverage for this security attribute — it cannot catch a `noreferrer`-only regression.

**Fix:** Add `noreferrer` assertions to the unit test to match E2E coverage:

```ts
expect(githubRel).toContain('noopener');
expect(githubRel).toContain('noreferrer');   // add this line

expect(linkedinRel).toContain('noopener');
expect(linkedinRel).toContain('noreferrer'); // add this line
```

### WR-03: `Masthead` "Engineer view" button has no `aria-label` — screen reader announces "Engineer view ↗"

**File:** `src/components/recruiter/Masthead.tsx:21-28`

**Issue:** The "Engineer view" button in `Masthead` has no `aria-label` or `title` attribute. Its accessible name is composed from its text children: `"Engineer view"` + `"↗"`, which a screen reader will announce as "Engineer view ↗". The arrow character `↗` has no inherent semantics and will be read literally. In contrast, the corresponding `TopBar` "Recruiter view" button has `aria-label="Switch to recruiter view"` (TopBar.tsx line 134), making its purpose unambiguous. The inconsistency is a WCAG 2.1 SC 2.4.6 (Headings and Labels) quality issue and risks false-negatives in automated axe scans because the button does have *some* accessible name.

**Fix:**
```tsx
<button
  type="button"
  className={styles.mastheadSwitch}
  onClick={onSwitchToIDE}
  aria-label="Switch to engineer / IDE view"
>
  <span aria-hidden="true">Engineer view</span>
  <span className={styles.arrow} aria-hidden="true">↗</span>
</button>
```

### WR-04: Duplicate test ID `REC-01` within the same `describe` block in `recruiter.spec.ts`

**File:** `e2e/recruiter.spec.ts:11` and `e2e/recruiter.spec.ts:19`

**Issue:** Two tests in the `'Recruiter view'` describe block share the name prefix `REC-01:`. Playwright test names within a describe block must be unique for unambiguous filtering (`--grep`), HTML report identity, and CI log readability. Running `npx playwright test --grep "REC-01"` will execute both tests, which may be surprising if a developer intends to run only one. Playwright does not error on duplicates; both run silently.

**Fix:** Rename the second test to a distinct ID:

```ts
// Line 11 — keep as is:
test('REC-01: shows masthead wordmark and Engineer view pill', ...)

// Line 19 — rename:
test('REC-01b: clicking Engineer view switches to IDE', ...)
// or assign the next available ID:
test('REC-06: clicking Engineer view switches to IDE', ...)
```

### IN-02: Clock interval fires every 30 seconds but initial time could be stale by up to 30 seconds

**File:** `src/components/ide/TopBar.tsx:44-51`

**Issue:** The `setInterval` period is 30 000 ms. The clock is initialised at mount time and then ticks every 30 s. If the component mounts at second :29, the clock will be visually wrong for up to 29 seconds before the first tick corrects it. This is a cosmetic UI issue on an ornamental clock widget; it is minor but worth noting given the care taken elsewhere in this component.

**Fix:** Align the first tick to the top of the next half-minute, or simply reduce the interval to 1 000 ms (1 s). The performance cost of a 1 s string-format is negligible:

```ts
const id = setInterval(tick, 1_000);
```
